Interview Tip
A common question is:
    
Q) Why do we drain a worker node before upgrading?
Draining safely evicts application pods and reschedules them onto other available nodes. This prevents workload disruption during the node upgrade and supports rolling upgrades with minimal downtime.

Q) Do you drain a control plane node before upgrading it? Why or why not?"
Expected answer:
It depends. If the control plane node only runs Kubernetes control plane components, draining provides little benefit because static pods such as kube-apiserver, etcd, scheduler, and controller-manager are not evicted. If workload pods are running on the control plane node, then draining is recommended to move those workloads before the upgrade.

Q) What happens to the API server during a control plane upgrade?"
The kube-apiserver static pod is restarted on the node being upgraded. In an HA cluster, the load balancer routes traffic to the remaining API servers, so the Kubernetes API remains available.


Q) Why do we upgrade only one control plane node at a time?"
To maintain API availability and etcd quorum. Upgrading multiple control plane nodes simultaneously could cause loss of quorum or insufficient API server capacity, leading to cluster instability.

Q) What happens if CP1 goes down during an upgrade?"
In an HA cluster, CP2 and CP3 continue serving API requests. Scheduler and controller-manager leader election selects a new leader if necessary, and etcd remains healthy as long as quorum is maintained.

Q) If drain does not evict static pods, what is the benefit of draining a control plane node?"
Draining only helps remove workload pods running on that node. It does not affect static pods. Therefore, the benefit depends on whether workloads are scheduled on the control plane node.

Q) "Can I upgrade all three control plane nodes simultaneously?"
NO. Control plane nodes should be upgraded sequentially. Upgrading multiple nodes at the same time can cause loss of API availability and etcd quorum.

Q) "How does etcd stay available when one control plane node is upgraded?" (L-3)
In a 3-member etcd cluster, quorum is 2. When one etcd member restarts during the upgrade, the other two members maintain quorum and continue serving requests.

Q) Why doesn't upgrading CP1 cause application downtime?"
Application workloads run on worker nodes. Control plane components are redundant in an HA setup. API requests are handled by remaining API servers, and workloads continue running during the control plane upgrade.

Q) "You upgraded CP1 and the API server restarted. Why didn't users notice any outage?"
Because the load balancer redirected traffic to the API servers running on CP2 and CP3 while CP1 was restarting.

Q) "What is the actual risk during a control plane upgrade?"
The biggest risk is losing etcd quorum or upgrading multiple control plane nodes simultaneously. That's why we verify cluster health, take an etcd backup, and upgrade one control plane node at a time.


Troubleshooting Questions
=========================

Q) Upgrade Stuck During kubeadm upgrade apply
    During kubeadm upgrade apply, the upgrade is stuck. What would you check?

Answer

    Check:
        kubectl get nodes
        kubectl get pods -A
    
    Check kubeadm logs:
        journalctl -xe

    Check kubelet:
        systemctl status kubelet
        journalctl -u kubelet -f

    Check static pods:
        crictl ps -a

    Look for:
        Image pull failures
        Certificate issues
        kubelet failures
        etcd connectivity problems


2. Node Becomes NotReady After Upgrade
Question
    After upgrading a worker node, it becomes NotReady. What would you do?

Answer
    Check:
        kubectl describe node <node>
    
    Check kubelet:
        systemctl status kubelet
        journalctl -u kubelet -f
    
    Verify version:
        kubelet --version
    
    Common causes:
        kubelet not restarted
        CNI issue
        certificate issue
        kubelet configuration mismatch


3. API Server Not Coming Up
Question
    After upgrading CP1, kube-apiserver is not starting.
Answer
    
    Check static pod status:
        crictl ps -a
    
    Check logs:
        crictl logs <container-id>
    
    Verify manifest:
        cat /etc/kubernetes/manifests/kube-apiserver.yaml
    
    Check certificates:
        kubeadm certs check-expiration

4. etcd Member Fails After Upgrade
Question
    One etcd member is not joining after upgrade.

Answer
    Check etcd pods:
        kubectl get pods -n kube-system
    
    Check etcd logs:
        crictl logs <etcd-container>
    
    Check cluster health:
        ETCDCTL_API=3 etcdctl endpoint health --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key

    Verify quorum is maintained.


5. Pods Not Scheduling After Upgrade
Question
    Upgrade completed but new pods are not getting scheduled.

Answer
    Check scheduler:
        kubectl get pods -n kube-system
    
    Check scheduler logs:
        crictl logs <scheduler-container>
    
    Check events:
        kubectl get events -A --sort-by=.metadata.creationTimestamp

    Possible causes:
        Scheduler not running
        Resource shortage
        Taints
        Node NotReady

6. Cluster Upgrade Successful but Applications Are Down
Question
    Cluster is healthy but application is unavailable after upgrade.

Answer
    Check:
        kubectl get pods -A
        kubectl describe pod <pod>
        kubectl logs <pod>
    
    Verify:
        Readiness probes
        Service endpoints
        Ingress
        Network policies

7. Worker Node Drain Fails
Question
    kubectl drain hangs or fails. What would you check?

Answer
    Most common reason:
        PodDisruptionBudget (PDB)

    Check:
        kubectl get pdb -A
    
    Example:
        Allowed disruptions: 0

    Drain cannot evict the pod.
    
    Also check:
        kubectl describe pod <pod>
